1

Un motor, un contrato

docengine es un motor determinista en Go que evalúa y mantiene la documentación de un repositorio a partir de un perfil versionado. Cada comprobación parte de un contrato explícito, nunca de inferencias.

Contratos documentales

Comprueba identificadores, referencias [[ID]], encabezados y cobertura sobre los documentos gobernados.

Hechos contrastados

Extrae valores de fuentes declaradas y contrasta cada afirmación del documento contra esas fuentes.

Capacidades opcionales

Impacto de cambios Git y recuperación léxica BM25, ambos desactivables por ejecución.

Solo lectura

La auditoría no escribe archivos, no modifica el índice Git y nunca accede a la red.

2

Cómo audita docengine

Una auditoría recorre fases secuenciales y deterministas. El núcleo no importa paquetes de CLI, Git ni skill; los adaptadores dependen del núcleo, nunca al revés.

Arquitectura hexagonal ligera

El núcleo recibe datos normalizados y produce resultados; la CLI, el sistema de archivos, Git y la salida son adaptadores.

01

Preparar

Define el alcance y reúne solo la documentación autorizada.

  1. 1

    Cargar y validar el perfil

    Rechaza campos desconocidos y normaliza las rutas relativas antes de leer el corpus.

  2. 2

    Resolver los documentos

    Selecciona los documentos en orden de ruta y lee solo Markdown dentro de la raíz autorizada.

02

Comprobar

Aplica contratos deterministas y contrasta los hechos declarados.

  1. 3

    Aplicar reglas deterministas

    Identificadores, referencias, cobertura y secciones, en el orden definido por el contrato.

  2. 4

    Evaluar hechos

    Resuelve cada fact, exige concordancia entre fuentes y evalúa los targets configurados.

03

Emitir

Agrega capacidades opcionales y produce el informe final.

  1. 5

    Agregar capacidades opt-in

    Git impact y BM25 añaden resultados sin cambiar la semántica de los findings deterministas.

  2. 6

    Serializar y salir

    Emite el informe en terminal o JSON y devuelve el código de salida derivado del resultado.

3

Tu primera auditoría

Compila la CLI desde el código fuente, inicializa el proyecto y ejecuta tu primera auditoría.

Primera auditoría 
go build -o docengine ./cmd/docengine
./docengine init --root .
./docengine status --root .
./docengine audit --root . \
  --profile .docengine/profile.json \
  --format terminal
Después de la primera auditoría 
./docengine plan --root .
./docengine apply --root . --yes
./docengine version

Importante

audit recibe siempre --profile de forma explícita; el perfil mínimo que propone init no declara documentos y audita cero archivos. Añade reglas para que el motor compruebe contratos.

5

Contratos deterministas

El perfil es el contrato del proyecto: un archivo JSON donde declaras qué documentos gobiernas y qué debe comprobar docengine. Sus campos se validan antes de leer el corpus.

El perfil agrupa las comprobaciones en bloques. Cada bloque es opcional: si no aparece, esa comprobación no se ejecuta, así que puedes empezar con un perfil mínimo y añadir reglas.

Documentos

documents

Reglas que cada documento gobernado debe cumplir: identificadores, referencias, encabezados e idioma.

Cobertura

coverage

Cada identificador definido en un documento origen debe estar referenciado por un documento destino.

Hechos

facts

Afirmaciones del documento contrastadas contra valores leídos de fuentes declaradas.

Exclusiones

exclusions

Rutas fuera de toda comprobación, cada una con un motivo declarado.

Impacto Git

impact_relations

Relaciona cambios de código con documentos para recomendar su revisión; requiere --base-ref.

BM25

bm25

Búsqueda léxica advisory que propone posibles duplicados o cobertura; nunca crea findings.

La severidad es error, warning o info; solo los findings error cambian el código de salida.

Códigos de finding deterministas

Cuando una comprobación no se cumple, docengine emite un finding: un aviso con un código estable, su ubicación y su mensaje.

Reglas de documento

Identificadores, referencias, encabezados e idioma sobre el Markdown gobernado.

  • ID_MISSING

    Un encabezado gobernado no tiene su identificador.

  • ID_MALFORMED

    El identificador no sigue el patrón (id_pattern) que exige la regla.

  • ID_DUPLICATE

    El mismo identificador está definido en más de un lugar.

  • REFERENCE_MALFORMED

    Un token [[…]] no es una referencia [[ID]] válida.

  • REFERENCE_TARGET_MISSING

    Una referencia apunta a un identificador que no existe en ningún documento.

  • SECTION_MISSING

    Falta un encabezado requerido declarado por la regla.

  • LANGUAGE_MISMATCH

    El idioma detectado no es el que declara el perfil (language).

  • LANGUAGE_UNDETERMINED

    El idioma detectado no es concluyente, así que no puede comprobarse.

  • LINK_TARGET_MISSING en preparación

    Un destino de enlace (relativo al documento o a la raíz) no existe, escapa por encima de la raíz de auditoría o cruza un enlace simbólico.

  • LINK_ANCHOR_MISSING en preparación

    El #fragment de un enlace no se resuelve en un encabezado del documento destino.

  • LINK_SCHEME_INVALID en preparación

    Una URL externa no tiene esquema (es //host) o usa uno distinto de http/https; mailto: y cualquier otro esquema son inválidos.

Cobertura

Relaciones fuente→destino, independientes del contrato de documento.

  • COVERAGE_MISSING

    Ningún documento destino menciona un identificador definido en el origen.

Hechos

Hechos contrastados contra fuentes declaradas; los fallos de fuente son siempre error.

  • FACT_SOURCE_MISSING

    Una ruta o glob de fuente no coincidió con nada.

  • FACT_SOURCE_INVALID

    Una fuente no pudo leerse ni analizarse.

  • FACT_SOURCE_MISMATCH

    Las fuentes produjeron valores en desacuerdo.

  • FACT_CLAIM_MISSING

    El documento no contiene la afirmación esperada para el hecho.

  • FACT_CLAIM_AMBIGUOUS

    Un target contiene afirmaciones distintas repetidas para un hecho.

  • FACT_VALUE_MISMATCH

    El valor afirmado no coincide con el de la fuente.

  • FACT_SET_MISMATCH

    La lista afirmada no coincide con la de la fuente.

6

Capacidades opcionales

Estas dos comprobaciones están desactivadas por defecto: solo se ejecutan si las habilitas en el perfil. Si las habilitas pero no pueden ejecutarse, docengine devuelve un error operativo; nunca las omite en silencio.

Impacto Git

Recomienda revisar los documentos que tocan las rutas cambiadas. Requiere --base-ref y nunca cambia el código de salida: es una recomendación, no un error. En el informe el código es GIT_IMPACT (severidad warning) y en terminal se imprime con el prefijo ADVISORY Git impact.

Búsqueda léxica (BM25)

Propone documentos candidatos a revisar por parecido léxico: posibles duplicados (possible_duplicate), cobertura (potential_coverage) o impacto (potential_impact). Cada candidato llega con estado needs_review y en terminal se imprime con el prefijo ADVISORY BM25. El perfil puede filtrarlos con min_score y acknowledged. Nunca crea findings ni cambia el código de salida.

exit 0 no equivale a ausencia de findings: revisa el informe completo y conserva visibles todos los findings con su severidad, ubicación, código y mensaje.

7

Códigos de salida estables

Cada ejecución termina con un código que resume el resultado: los scripts y los hooks deciden con él si continuar o detenerse.

0

Sin errores deterministas

Sin findings deterministas de severidad error; puede incluir warning. No significa ausencia de findings.

1

Hallazgos de error

Existe al menos un finding determinista de severidad error.

2

Uso o configuración inválidos

Uso o configuración inválidos: flags, JSON, rutas, versión de perfil o colisión no autorizada de init.

3

Fallo operativo

Fallo operativo no representable: I/O, Git solicitado no disponible o un módulo opcional fallido.

Un fallo nunca devuelve 0. Los códigos 2 y 3 no se mezclan con findings del repositorio.

8

El perfil y el informe

El perfil declara qué se comprueba; el informe declara qué se encontró. Son los dos JSON estables con los que trabajas.

El perfil es el contrato que viste en Contratos. Estos son todos sus campos.

  • versionobligatorio

    Siempre 1; identifica la versión del contrato.

  • languageobligatorio

    Idioma de la prosa gobernada: en o es. Las reglas sin language propio lo heredan.

  • strict_confirmationopcional

    Si es true (valor por defecto), la skill pide confirmar antes de cada commit.

  • documentsopcional

    Reglas por documento. Cada regla lleva globs (qué archivos), id_pattern (patrón del identificador), severity (error por defecto), required_headings, language y checks (ids, references, headings, language, links).

    en preparación

    checks acepta cadenas simples como "ids" u objetos como {"name": "links", "severity": "error"}. Una cadena u objeto sin severity usa la severidad de la regla; la del objeto solo sobrescribe esa comprobación. Los nombres deben ser uno de los cinco checks, sin duplicados. Para sobrescribir una comprobación y mantener las demás con la severidad de la regla debes enumerarlas: omitir checks ejecuta todas y no permite adjuntar una sobrescritura; enumerarlas tampoco selecciona automáticamente futuras comprobaciones.

  • coverageopcional

    Relaciones sources → targets con severity: cada identificador del origen debe estar referenciado en el destino, o el motor emite COVERAGE_MISSING.

  • factsopcional

    Hechos a contrastar. Cada hecho lleva id, sources (tipos path_count, path_set, directory_set, frontmatter_set, text_value, json_count, regex_set) y targets (value, set, contains_source_set).

    en preparación

    regex_set lleva path, pattern y value_type; produce el conjunto de cada coincidencia capturada por el grupo con nombre value de pattern. Cero coincidencias es FACT_SOURCE_MISSING; los duplicados se colapsan y se ignora el orden; varias fuentes deben producir el mismo conjunto o el hecho emite FACT_SOURCE_MISMATCH.

  • exclusionsopcional

    Globs excluidos de toda comprobación. La reason es obligatoria.

  • impact_relationsopcional

    Relaciona documents con paths cambiadas para recomendar su revisión. Requiere --base-ref.

  • bm25opcional

    Avisos léxicos. Campos: enabled, documents, capabilities (duplicates, coverage, impact), max_candidates, title_weight, body_weight, min_score y acknowledged.

Ejemplo mínimo (init) 
{
  "version": 1,               // versión del contrato: siempre 1
  "language": "en",           // idioma de la prosa: "en" o "es"
  "strict_confirmation": true  // confirmar antes de cada commit (true por defecto)
}
Ejemplo completo (comentado) 
{
  // Obligatorios.
  "version": 1,
  "language": "en",
  // Confirmar antes de cada commit (true por defecto).
  "strict_confirmation": true,

  // Reglas por documento.
  "documents": [
    {
      "globs": ["docs/**/*.md"],                // archivos que gobierna
      "id_pattern": "^[A-Z][A-Z0-9]*-[0-9]+$",  // patrón del identificador
      "required_headings": ["Overview"],         // encabezados obligatorios
      "language": "en",
      "severity": "error"                        // error | warning | info
    }
  ],

  // Cada identificador del origen debe estar referenciado en el destino.
  "coverage": [
    { "sources": ["docs/specs/**/*.md"], "targets": ["docs/index.md"], "severity": "warning" }
  ],

  // Afirmaciones contrastadas contra fuentes declaradas.
  "facts": [
    {
      "id": "catalog.count",
      "sources": [
        { "kind": "path_count", "glob": ["catalog/*.md"] },
        { "kind": "json_count", "path": "data/manifest.json", "field": "entries" }
      ],
      "targets": [
        { "paths": ["README.md"], "pattern": "Catalog count: (?P<value>[0-9]+)", "value_type": "integer" }
      ]
    }
  ],

  // Rutas fuera de toda comprobación; "reason" es obligatoria.
  "exclusions": [
    { "globs": ["vendor/**"], "reason": "documentación de terceros, fuera de este contrato" }
  ],

  // Relaciona cambios de código con documentos (requiere --base-ref).
  "impact_relations": [
    { "documents": ["docs/**/*.md"], "paths": ["internal/**", "cmd/**"], "reason": "el código puede invalidar lo documentado" }
  ],

  // Avisos léxicos advisory: nunca crean findings.
  "bm25": {
    "enabled": true,
    "documents": ["docs/**/*.md"],
    "capabilities": ["duplicates", "coverage", "impact"],
    "max_candidates": 10,
    "min_score": 50,
    "acknowledged": [
      { "relation": "possible_duplicate", "pair": ["docs/a.md", "docs/b.md"], "reason": "revisado y aceptado" }
    ]
  }
}

El informe es lo que devuelve una auditoría. Estos son sus campos.

  • findingssiempre

    Lista de resultados. Cada finding lleva severity (error, warning o info), code, path, line y message. Solo error cambia el código de salida.

  • summarysiempre

    Recuentos: checked_files (documentos revisados) y counts por severidad (info, warning, error).

  • facts · impact · bm25aditivo

    Aparecen solo si su módulo está activo; nunca cambian findings ni summary.

Ejemplo de informe 
{
  // Cada comprobación fallida es un finding.
  "findings": [
    {
      "severity": "error",   // error | warning | info (solo "error" cambia la salida)
      "code": "ID_MISSING",  // código estable
      "path": "docs/guide.md",
      "line": 1,
      "message": "governed heading has no document identifier"
    }
  ],
  // Recuentos del resumen.
  "summary": {
    "checked_files": 1,
    "counts": { "info": 0, "warning": 0, "error": 1 }
  }
}
9

Diátaxis: cuatro rutas de documentación

Diátaxis es la técnica que clasifica la documentación por lo que necesita quien la consulta. La ordenan dos ejes —aprender o trabajar, hacer o comprender— y cada documento sirve a una sola.

Sin un criterio así, la documentación mezcla instrucciones, datos y explicaciones en un mismo texto y cuesta usarla. Diátaxis separa esas necesidades y obliga a que cada documento tenga un único propósito. El motor lo adopta por eso: un documento con un propósito claro y una carpeta asignada puede auditarse como el resto de contratos (cobertura, encabezados, idioma).
